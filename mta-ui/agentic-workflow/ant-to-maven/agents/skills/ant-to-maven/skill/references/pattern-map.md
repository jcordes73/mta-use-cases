# Pattern Map — Apache Ant to Apache Maven

Build-pattern changes that are not simple renames: structural build-file refactors, behavioral changes, additions.

| description | category | detect_pattern | before | after | notes | source_section |
|---|---|---|---|---|---|---|---|
| build.xml targets replaced by Maven lifecycle phases: Ant `target`+`depends` → phases/goals bound by the lifecycle; `depends` chains (`dist depends=compile, test`) reveal implicit package-and-verify ordering | structural | `<target name=` | `<target name="compile" depends="init">...<javac .../></target>` | lifecycle ordering: `mvn package` runs everything up to `package`; never declare that jar depends on compile — built into the lifecycle | Core mapping: `javac`→maven-compiler-plugin (compile), `jar`→maven-jar-plugin (package), `war`→maven-war-plugin, `copy`+`filterset`→maven-resources-plugin, `delete`/`mkdir`→maven-clean-plugin (usually deleted, not converted), `junit`→maven-surefire-plugin, `javadoc`→maven-javadoc-plugin, `zip`/`tar`→maven-assembly-plugin, fat jar→maven-shade-plugin, everything else→maven-antrun-plugin | Phase 3: Map Build Steps to Plugins |
| `clean` target that deletes build/ and dist/ is deleted, not converted | removal | `<delete dir=` | `<target name="clean"><delete dir="${build.dir}"/></target>` | `mvn clean` (clean lifecycle, built in); `target/` created on demand and wiped by `mvn clean` | Only convert a `delete` target if it removes something other than build output | Phase 3: Map Build Steps to Plugins |
| Ant `jar` target with manifest → maven-jar-plugin `archive` configuration | structural | `<jar destfile=` | `<jar destfile="dist/acme-core-1.0.0.jar" basedir="${build.dir}/classes"><manifest><attribute name="Main-Class" value="com.acme.Core"/><attribute name="Implementation-Version" value="1.0.0"/></manifest></jar>` | `<plugin><groupId>org.apache.maven.plugins</groupId><artifactId>maven-jar-plugin</artifactId><configuration><archive><manifest><mainClass>com.acme.Core</mainClass><addDefaultImplementationEntries>true</addDefaultImplementationEntries></manifest></archive></configuration></plugin>` | No `destfile`/`basedir`: jar is always `target/<finalName>.jar` from `target/classes/`; pull versions from coordinates, not hard-coded values; prefer one artifact per module over per-jar includes/excludes | Phase 3: Map Build Steps to Plugins |
| Ant `copy` with `<filterset>` → maven-resources-plugin filtering on `src/main/resources` | structural | `<filterset>` | `<copy todir="${build.dir}/classes" filtering="true"><fileset dir="config"/><filterset><filter token="project.version" value="1.0.0"/></filterset></copy>` | `<build><resources><resource><directory>src/main/resources</directory><filtering>true</filtering></resource></resources></build>` with `@project.artifactId@`, `@project.version@` tokens in resources | Filtering is per-resource-directory; binary files in a filtered directory get corrupted — split them into a second `<resource>` entry with filtering off; avoid timestamp tokens (break reproducible builds); `@java.version@` resolves from the build JVM, not the target version | Phase 3: Map Build Steps to Plugins |
| Distribution `zip`/`tar` targets → maven-assembly-plugin with descriptor | structural | `<zip destfile=` | `<zip destfile="dist/acme-core-1.0.0-distribution.zip"><zipfileset dir="dist" includes="acme-core-1.0.0.jar"/>...</zip>` | `<plugin><artifactId>maven-assembly-plugin</artifactId><configuration><descriptorRefs><descriptorRef>jar-with-dependencies</descriptorRef></descriptorRefs><archive><manifest><mainClass>com.acme.Core</mainClass></manifest></archive></configuration><executions><execution><id>make-assembly</id><phase>package</phase><goals><goal>single</goal></goals></execution></executions></plugin>` | `jar-with-dependencies` needs no descriptor file; custom descriptors live under `src/assembly/` versioned with the code; `<fileSets>` with `<directoryMode>`/`<fileMode>` is the direct `zipfileset` translation | Phase 3: Map Build Steps to Plugins |
| Fat-jar merges (unpack-everything-into-one-jar) → maven-shade-plugin with ServicesResourceTransformer | structural | `<unzip dest=` | `<target name="onejar" depends="jar,resolve-libs"><unzip dest="${build.dir}/onejar"><fileset dir="lib" includes="*.jar"/></unzip>...<jar destfile="dist/acme-core-1.0.0-onejar.jar" basedir="${build.dir}/onejar"/></target>` | `<plugin><artifactId>maven-shade-plugin</artifactId><executions><execution><phase>package</phase><goals><goal>shade</goal></goals><configuration><transformers><transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer"/><transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer"><mainClass>com.acme.Core</mainClass></transformer></transformers></configuration></execution></executions></plugin>` | The Ant merge silently drops colliding `META-INF/services/` files (last-unpacked wins); shade's ServicesResourceTransformer concatenates them; shade works from the POM dependency graph, not `lib/` | Phase 3: Map Build Steps to Plugins |
| Codegen targets writing to scratch dirs → build-helper-maven-plugin `add-source` (or a dedicated generator plugin) | structural | `<java classname=.*CodeGen` | `<target name="codegen" depends="init"><mkdir dir="build/gen"/><java classname="com.acme.tools.CodeGen" fork="true"><arg value="-o"/><arg value="build/gen"/></java></target>` | build-helper-maven-plugin execution at phase `generate-sources` with `<goal>add-source</goal>` and `<source>target/generated-sources/acme</source>` | Register output under `target/generated-sources/` (IDEs exclude it from refactoring); prefer dedicated plugins: `jaxb2-maven-plugin`/`maven-jaxb2-plugin` for JAXB, `antlr4-maven-plugin` for ANTLR — they register their output automatically; generation must run before `add-source` (generate-sources phase guarantees this) | Phase 3: Map Build Steps to Plugins |
| Ant `<junit>` blocks with hand-assembled classpath and `<batchtest>` → Surefire defaults | structural | `<junit printsummary=` | `<target name="test" depends="compile-tests"><mkdir dir="${build.dir}/test-reports"/><junit printsummary="yes" haltonfailure="yes"><classpath>...</classpath><batchtest todir="${build.dir}/test-reports"><fileset dir="${test.dir}"><include name="**/*Test.java"/></fileset></batchtest><formatter type="xml"/></junit></target>` | `mvn test`; Surefire discovers `*Test`, `Test*`, `*Tests`, `*TestCase` in `src/test/java`; reports under `target/surefire-reports/`; haltonfailure is the default | Rename nonconforming test classes (e.g. `LegacyChecks`) or add explicit `<includes>` and delete it as they are renamed; configure Surefire only to override defaults (e.g. `<excludes><exclude>**/*SlowTest.java</exclude></excludes>`); TestNG also auto-detected, `<suiteXmlFiles>` for XML suites | Phase 4: Migrate Tests |
| Test fixtures copied by Ant `<copy>` steps → `src/test/resources` | structural | `src/test/resources` absent while fixtures exist | fixtures copied into the test classpath dir, wired into `test` target's `depends` chain | Move files to `src/test/resources`; copied by `process-test-resources` automatically; add `<filtering>true</filtering>` if fixtures contain tokens | Same filtering rules as main resources | Phase 4: Migrate Tests |
| JaCoCo Ant coverage wrapping (`jacoco:coverage` around `<junit>` + separate `jacoco:report`) → jacoco-maven-plugin executions | structural | `jacoco:coverage` | `<target name="coverage" depends="compile-tests" xmlns:jacoco="antlib:org.jacoco.ant"><jacoco:coverage destfile="${build.dir}/jacoco.exec"><junit>...</junit></jacoco:coverage></target>` | `<plugin><groupId>org.jacoco</groupId><artifactId>jacoco-maven-plugin</artifactId><executions><execution><id>prepare-agent</id><goals><goal>prepare-agent</goal></goals></execution><execution><id>report</id><phase>verify</phase><goals><goal>report</goal></goals></execution></executions></plugin>` | `mvn verify` runs tests then produces the HTML report under `target/site/jacoco`; Cobertura is effectively unmaintained — do not port it | Phase 4: Migrate Tests |
| Separate `itest` target for integration tests → maven-failsafe-plugin with `*IT` naming | structural | `**/*IT.java` | `<target name="itest" depends="jar"><junit>...<batchtest todir="${build.dir}/itest-reports"><fileset dir="${test.dir}"><include name="**/*IT.java"/></fileset></batchtest></junit></target>` | `<plugin><artifactId>maven-failsafe-plugin</artifactId><executions><execution><goals><goal>integration-test</goal><goal>verify</goal></goals></execution></executions></plugin>` | `integration-test` and `verify` goals split so cleanup can run between them; reports under `target/failsafe-reports/`; delete the `itest` target | Phase 4: Migrate Tests |
| WAR staged by hand (`<war>` task assembling WEB-INF/lib, classes, webres) → `<packaging>war</packaging>` + maven-war-plugin defaults | structural | `<war destfile=` | `<target name="war" depends="compile, resolve-libs"><mkdir dir="${build.dir}/webapp/WEB-INF"/><war destfile="dist/acme-web-1.0.0.war" webxml="config/web.xml"><fileset dir="${build.dir}/webapp"/><lib dir="${lib.dir}"><include name="*.jar"/><exclude name="servlet-api*.jar"/></lib><classes dir="${build.dir}/classes"/><webres dir="src/webres"/></war></target>` | `<packaging>war</packaging>`; `src/main/webapp` holds JSPs, static assets, `WEB-INF/web.xml`; servlet API `provided`-scoped; no staging directory, no copy targets, no `war` task | `warSourceDirectory`/`webXml` overrides only for legacy layouts; the plugin block is redundant on the standard layout; `<overlay>` merges another WAR deterministically when the Ant build did unzip-and-recopy | Packaging Web Applications (WAR) |
| Ant deploy/start/stop targets (copy WAR to container, shell-scripted `<exec>` around startup.sh/shutdown.sh) → Cargo plugin | structural | `startup.sh` or `<exec executable=` with catalina.home | `<target name="container-test" depends="war"><exec executable="${catalina.home}/bin/startup.sh"/><waitfor maxwait="30" maxwaitunit="second"><http url="http://localhost:8080/acme-web/health"/></waitfor>...<exec executable="${catalina.home}/bin/shutdown.sh"/></target>` | `org.codehaus.cargo:cargo-maven3-plugin` with `<container><containerId>tomcat10x</containerId></container>`; goals `cargo:start`/`cargo:run`/`cargo:stop` or bound to pre-/post-integration-test phases | Container-native alternatives: `org.wildfly.plugins:wildfly-maven-plugin`, `org.glassfish.embedded:maven-embedded-glassfish-plugin`; `mvn deploy` (repository publish) is unrelated to Cargo's container deploy despite sharing a verb | Packaging Web Applications (WAR) |
| Hand-wired container tests → Arquillian deployments under Failsafe | structural | `@Deployment` absent with container-test targets present | start container, deploy WAR, run JUnit suite, tear down — all scripted in the target | test class declares `@Deployment` returning a shrinkwrap archive; `arquillian-junit5-container` + container adapter as test-scoped deps; runs under Failsafe like any `*IT` | Delete the shell-scripted `container-test` target | Packaging Web Applications (WAR) |
| Hand-assembled EAR staging (copy modules + hand-maintained application.xml, `<ear>` task) → `<packaging>ear</packaging>` + maven-ear-plugin | structural | `<ear destfile=` | `<target name="ear" depends="dist"><mkdir dir="${build.dir}/ear/META-INF"/><copy file="config/application.xml" todir="${build.dir}/ear/META-INF"/><ear destfile="dist/acme-1.0.0.ear" appxml="${build.dir}/ear/META-INF/application.xml"><fileset dir="acme-web/dist" includes="acme-web-1.0.0.war"/><fileset dir="acme-core/dist" includes="acme-core-1.0.0.jar"/><fileset dir="${lib.dir}" includes="commons-lang3-3.14.0.jar"/></ear></target>` | `<plugin><artifactId>maven-ear-plugin</artifactId><configuration><generateApplicationXml>true</generateApplicationXml><defaultLibBundleDir>lib/</defaultLibBundleDir><modules><webModule><groupId>com.acme</groupId><artifactId>acme-web</artifactId><contextRoot>/acme</contextRoot></webModule><jarModule><groupId>com.acme</groupId><artifactId>acme-core</artifactId></jarModule></modules></configuration></plugin>` | `generateApplicationXml` (default true) writes META-INF/application.xml from the `<modules>` list; EAR module declares `<dependencies>` on siblings with `<type>war</type>`; only makes sense in a multi-module build | Packaging Enterprise Applications (EAR) |
| Duplicated jars across WAR `WEB-INF/lib` and EAR `lib/` → skinny wars | behavioral | `<skinnyWars>` absent in multi-module EAR builds | default assembly ships one copy of each shared jar per web module plus one in EAR `lib/` | `<defaultLibBundleDir>lib/</defaultLibBundleDir><skinnyWars>true</skinnyWars>` strips shared jars out of the wars; `<excludeLibs>` for per-module exceptions | `skinnyWars` changes classloading: war must see EAR-level `lib/` (the `library-directory` default guarantees this); deliberately different per-war versions become explicit `<excludeLibs>`/`<bundleFileName>` config | Packaging Enterprise Applications (EAR) |
| Custom `<taskdef>` invocations → maven-antrun-plugin execution with task jar in plugin `<dependencies>` | structural | `<taskdef` | `<target name="version-stamp" depends="compile"><taskdef name="version-stamp" classname="com.acme.build.VersionStampTask" classpath="${build.dir}/classes"/><version-stamp version="1.0.0" outfile="${build.dir}/classes/version-stamp.properties"/></target>` | `<plugin><artifactId>maven-antrun-plugin</artifactId><dependencies><dependency><groupId>com.acme</groupId><artifactId>acme-build-tools</artifactId><version>1.0.0</version></dependency></dependencies><executions><execution><id>version-stamp</id><phase>process-classes</phase><goals><goal>run</goal></goals><configuration><target><taskdef name="version-stamp" classname="com.acme.build.VersionStampTask"/><version-stamp version="${project.version}" outfile="${project.build.outputDirectory}/version-stamp.properties"/></target></configuration></execution></executions></plugin>` | Strategy ladder: (1) find a plugin equivalent first (resources, enforcer, generator plugins — see Appendix A), (2) wrap with antrun, (3) rewrite as a mojo or `exec-maven-plugin`. Wrapping acceptable indefinitely only for lifecycle-external side effects (build-info files, notifications, changelogs); never for compile-classpath, test-execution, or artifact-assembly steps — those must become native Maven before cutover | Phase 5: Custom Ant Tasks and the Antrun Escape Hatch |
| Raw `<exec>`/`<java fork="true">` process invocations → exec-maven-plugin goals | structural | `<exec executable=` | `<target name="generate-schema"><java classname="com.acme.tools.SchemaGenerator" fork="true"><classpath>...</classpath><arg value="-out"/><arg value="${build.dir}/schema"/></java><exec executable="gzip"><arg value="${build.dir}/schema/catalog.sql"/></exec></target>` | `<plugin><groupId>org.codehaus.mojo</groupId><artifactId>exec-maven-plugin</artifactId><executions><execution><id>generate-schema</id><phase>generate-resources</phase><goals><goal>java</goal></goals><configuration><mainClass>com.acme.tools.SchemaGenerator</mainClass><arguments><argument>-out</argument><argument>${project.build.directory}/schema</argument></arguments><classpathScope>compile</classpathScope></configuration></execution><execution><id>gzip-schema</id><phase>generate-resources</phase><goals><goal>exec</goal></goals><configuration><executable>gzip</executable><arguments><argument>${project.build.directory}/schema/catalog.sql</argument></arguments></configuration></execution></executions></plugin>` | `exec:java` does NOT fork — if the step relies on forking for isolation (System.exit, static state, classloader separation), use the `exec` goal with a `java` executable; prefer exec-maven-plugin over antrun containing `<java>`/`<exec>`; generators bind to `generate-resources`/`generate-sources` (before compile) | Phase 5: Custom Ant Tasks and the Antrun Escape Hatch |
| Multi-module driver script (`<subant>` or repeated `<ant antfile=...>`) → aggregator POM with `<modules>` + reactor | structural | `<subant` | `<project name="acme-build" default="dist" basedir="."><target name="clean"><subant target="clean"><fileset dir="." includes="acme-core/build.xml"/><fileset dir="." includes="acme-web/build.xml"/></subant></target><target name="dist"><subant target="dist" verbose="true"><fileset dir="." includes="acme-core/build.xml"/></subant><subant target="dist" verbose="true"><fileset dir="." includes="acme-web/build.xml"/></subant></target></project>` | `<packaging>pom</packaging>` aggregator with `<modules><module>acme-core</module><module>acme-web</module></modules>`; reactor derives build order from dependency declarations; delete the driver script | Module list appears exactly once; partial builds: `mvn -pl acme-web -am package` (also-make), `mvn -pl acme-core -amd package` (also-make-dependents); building from inside one module falls back to the local repository | Phase 6: Multi-Module Builds |
| Shared config via `common.properties` + copy-pasted blocks → parent POM inheritance | structural | `<property file="../common.properties"/>` | each module's build.xml loads `../common.properties` and copy-pastes `<path>`/`<macrodef>` blocks that drift | parent POM `<properties>` inherited outright + `<dependencyManagement>` declaring shared versions; children opt in with `<parent>` element, declare deps without versions | `<dependencyManagement>` does NOT add dependencies to children — it pins versions for artifacts children declare; ends the copy-pasted-macrodef drift problem | Phase 6: Multi-Module Builds |
| Sibling jars referenced as filesystem paths (`<path>` at `../acme-core/dist/acme-core-1.0.0.jar`) → sibling dependency by GAV coordinates | structural | `../acme-core/dist` | `<path id="sibling.classpath"><pathelement path="../acme-core/dist/acme-core-1.0.0.jar"/></path>` | `<dependency><groupId>com.acme</groupId><artifactId>acme-core</artifactId><version>${project.version}</version></dependency>` | Reactor resolves the sibling from the current build; a changed API surfaces as a compile error on the next `mvn package`, not a stale-jar mystery | Phase 6: Multi-Module Builds |
| Ant CI job (`ant clean test jar`) → `mvn -B -ntp verify` | structural | `ant clean test` | `ant clean test jar` in the CI shell script | `mvn -B -ntp verify` (`-B` batch mode, `-ntp` no-transfer-progress) | Cache `~/.m2/repository` between builds (not all of `~/.m2`); builds must succeed on a cold cache; `mvn verify` exercises everything `package` does plus the gates | Phase 8: CI/CD and Release |
