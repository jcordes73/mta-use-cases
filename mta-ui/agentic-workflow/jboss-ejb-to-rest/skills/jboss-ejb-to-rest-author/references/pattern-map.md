# Pattern Map

Process rows by category: `structural` and `behavioral` rows locate affected code
via `detect_pattern`; `addition` rows introduce new artifacts.

| description | category | detect_pattern | before | after | notes | source_section |
|---|---|---|---|---|---|---|
| Provider: REST resource wraps the EJB, calling it over the **local view** so the REST request behaves like the old local call chain (pass-by-reference, shared transaction) | structural | `@Remote` | `@Remote public interface CustomerServiceRemote { CustomerDTO findCustomer(long id) throws CustomerNotFoundException; }` | `@Path("/api/v1/customers") @Produces(MediaType.APPLICATION_JSON) @RequestScoped public class CustomerResource { @EJB private CustomerServiceLocal customerService; @GET @Path("/{id}") public CustomerDTO getCustomer(@PathParam("id") long id) throws CustomerNotFoundException { return customerService.findCustomer(id); } }` | Check `@ApplicationPath("/api")` — resource paths are relative to it; effective URLs must match the OpenAPI document exactly. No local view? Add `@Local` interface or `@LocalBean` | §2.1, §2.2 |
| SOAP variant: additive REST facade over the SOAP-exposed EJB — local view preferred, SOAP endpoint as fallback; the EJB is never modified | structural | `@WebService` | `@WebService @Stateless public class CustomerServiceBean { @WebMethod public CustomerDTO findCustomer(long id) ... }` | `@Path("/api/v1/customers") @ApplicationScoped public class CustomerRestFacade { @EJB private CustomerServiceLocal customerService; ... }` (fallback: `@WebServiceRef` SOAP delegation in the same single injected field) | Delegate, don't duplicate — no business rules in the facade. `@WebMethod` signatures are the endpoint-design blueprint. WSDL + SOAP clients are never retired | §2.6 |
| Exceptions map to HTTP status + consistent JSON error body, one agreed contract | structural | `ExceptionMapper` | checked exceptions propagate over remoting / opaque `NoSuchEJBException` | `@Provider public class CustomerNotFoundExceptionMapper implements ExceptionMapper<CustomerNotFoundException> { toResponse → 404 + {"code":"CUSTOMER_NOT_FOUND","message":...} }` | §5.3 table: NotFound→404, Validation→400, Conflict→409, `EJBAccessException`→403, `NoSuchEJBException`/`ConnectException`→503 (transient → retry/circuit-break), unexpected→500. Register explicitly on the Application if auto-discovery fails | §2.2, §5.3 |
| Endpoint design: EJB method shapes map to REST resources | structural | `@WebMethod` | `findX(id)`, `searchX(filter)`, `createX(dto)`, `updateX(id,dto)`, `deleteX(id)`, `activateX(id)` | `GET /api/v1/X/{id}`, `GET /api/v1/X?filter=...`, `POST /api/v1/X` (201+Location), `PUT/PATCH /api/v1/X/{id}`, `DELETE /api/v1/X/{id}` (204), `POST /api/v1/X/{id}/activation` | Nouns not verbs; version prefix `/api/v1` from day one, never change a published operation in place; paginate large lists; `@Valid` on parameters for automatic 400s; binaries as `octet-stream`/`multipart`/`StreamingOutput`, not Base64-in-JSON by default | §2.3 |
| Optimistic locking over REST: version checks become ETag/If-Match | behavioral | `@Version` | `@Version` entity check inside the EJB | `ETag` header on GET responses, `If-Match` required on PUT/PATCH/DELETE, stale version → `412 Precondition Failed` | Reserve `409` for business-level conflicts; pick one convention and document it | §2.3, §5.3 |
| Transactions no longer span applications — cross-app flows need explicit design | behavioral | `@TransactionAttribute` | caller's logical operation spans the EJB call and local DB writes as one flow (or IIOP/XTS-propagated transaction) | order operations so the remote (non-transactional) call comes last; idempotent provider endpoints + retry; compensating action or saga; LRA on EAP XP 6.0+ for multi-step flows | Never "wrap" the REST call in the consumer's `@Transactional` and expect atomicity. `Idempotency-Key` on non-idempotent POSTs must be implemented properly (store key+result, bounded TTL, replay returns original outcome) | §5.2 |
| IIOP/XTS semantics have no REST replacement | behavioral | `corbaloc:` | `javax.rmi.*` / `org.omg.CORBA` imports; transactions and security propagated over IIOP | treat like any cross-app boundary (§5.2): remote call last, idempotent endpoint, compensation; caller's transaction commits even if the REST call fails | Same for XTS/WS-AT spanning applications — redesign the flow, don't preserve atomicity | §5.6 |
| `ejb:` URLs are coupled to *deployed* artifact names and to the client's process | behavioral | `ejb:` | `@EJB(lookup = "ejb:customer-app/customer-ejb/CustomerServiceBean!...")` | check every `ejb:` lookup against the actual deployment names during migration; for a consumer in the **same server**, use `java:global/<deployment-name>/<bean>!<view>` | Renamed deployments fail at invocation, not deploy: `EJBCLIENT000409`. In-server `ejb:` lookups never route in-VM (verified) | §3.1 |
| Consumer keeps an adapter seam (anti-corruption layer) — business code never touches HTTP | structural | `@RegisterRestClient` | business logic injects `CustomerServiceRemote` directly | `CustomerServiceAdapter implements CustomerService` delegating to the REST client; config-selected `@Alternative` rollback path back to the EJB during transition | One place to change if the provider API evolves; also the per-call-site rollback switch (remove once proven in production) | §3.6, §4.2 |
| Cutover is per call site, old and new paths live in parallel | structural | `@EJB` | all call sites on the remote EJB lookup | one call site switched to the REST client per step, verified, then the next; `@Remote` wiring, `jboss-ejb-client.xml`, `jndi.properties` deleted only after the last one | Never big-bang. Provider runs both endpoints in parallel against the same bean from the start | §4.1, §4.2 |
| Old paths are never removed as part of this migration | removal | `remote-outbound-connection` | `@Remote` interface, SOAP endpoint, remoting subsystem config | all kept and supported; retirement is a separate, audited §4.4 decision (access-log audit over a usage window incl. batch/month-end jobs) | Automation must not touch the old path | §4.4 |
| Explicit resilience on the adapter: timeouts, retries, circuit breaker | addition | `mp-rest/readTimeout` | implicit, server-configured EJB timeouts | `connectTimeout`/`readTimeout` per client; `@Retry`/`@CircuitBreaker`/`@Fallback`/`@Bulkhead` (MP Fault Tolerance, EAP XP) on the adapter | Retry only idempotent operations; `@Bulkhead` caps concurrency, protecting the provider from retry storms | §5.4 |
| Performance: batch endpoints and payload discipline | behavioral | `for` loop calling the EJB per item | `for (Long id : ids) { remote.findCustomer(id); }` | `GET /api/v1/customers?ids=1,2,3` batch endpoint; HTTP keep-alive/connection pooling; trimmed DTOs | REST + JSON per-call overhead is higher than binary remoting | §5.5 |
| Consumer acquires and attaches credentials per request (remoting identity propagation is gone) | addition | `ClientRequestFilter` | identity propagated transparently by the EJB remoting layer | OAuth2 **client-credentials grant** token cached until expiry (refresh on 401), attached via a `ClientRequestFilter`/MP-JWT filter; or `elytron-oidc-client` subsystem (base EAP) obtains/attaches tokens; or mTLS; basic auth over TLS as simplest fallback | Agree the mechanism with the provider team — same on both sides. Token endpoint example: `https://idp.example.com/realms/acme/protocol/openid-connect/token`; do not fetch a token per call | §3.5 |
| Correlation ID / distributed tracing across the boundary | addition | `X-Request-Id` | remoting carried at least the security identity; HTTP carries nothing | correlation ID generated/accepted per request, set in a server filter, forwarded in a `ClientRequestFilter`; OpenTelemetry `traceparent` (EAP XP) preferred | Log the ID on both sides; metrics per remote call live on the adapter | §5.8 |
| OpenAPI document is the published contract | addition | `openapi` | WSDL / shared remote-interface jar is the contract | static `META-INF/openapi.yaml` (static entries take precedence over generated) + `microprofile-openapi-smallrye` subsystem serving `/openapi`; consumers generate clients from it | `operationId` values are load-bearing — renaming one breaks every generated client (treat as breaking change). Manual fallback: tiny `@Path("/api/v1/openapi")` resource serving the file | §2.7 |
| WS-\* capabilities without REST equivalents keep those consumers on SOAP | behavioral | `WS-Security` | WS-Security signing/encryption, WS-ReliableMessaging, WS-AtomicTransaction/XTS, WS-Addressing, strict XSD validation, handler chains | consumers needing these stay on the SOAP endpoint (kept anyway); REST substitutes: TLS+mTLS+bearer tokens, retries+idempotency, saga/LRA, correlation IDs+202/polling, Bean Validation, JAX-RS filters | MTOM attachments → streaming bodies; `@Oneway` → `202` + async; RPC/encoded ops → re-modeled resources (worked example shows all of these) | §2.6 |
| Monolith split (§7) is a human-only decision | addition | | monolithic JEE app using EJBs internally | split only along real functional/business domain crossings with a concrete driver (deployability, scaling, failure isolation, compliance) — score candidates, record an ADR | Out of scope for automation: §7.1 scoring, boundary choice, sequencing are all human decisions; REST seams from this migration are where the boundaries go | §7 |
